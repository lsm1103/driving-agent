# 07 阶段 0 结果

日循环骨架（L1 World + L2 Ledger + 十步循环，Compete 用固定规则，Act 模拟执行）
在 8 天回放窗口上跑通。docs/03 §6 给阶段 0 定的三个观察问题全部有了答案，
其中两个答案是「否」。

## 1. ❌ 账本确实膨胀成垃圾场

docs/03 §6 问：「账本会不会膨胀成垃圾场？」——**会。**

| 天 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| 流入 | 4 | 6 | 4 | 8 | 4 | 5 | 6 | 1 |
| 闭合 | 2 | 2 | 0 | 0 | 0 | 2 | 2 | 2 |
| 未闭合累计 | 2 | 6 | 10 | 18 | 22 | 25 | 29 | 28 |

```
日均流入 4.75   （探针预测 4.8，测得很准）
日均闭合 1.25   ← 关键
净流入   +3.50/天   →   30 天外推 +105 条
```

### 错在哪：把「预算槽」当成了「闭合数」

[06](06-探针结果.md) §7.2 曾写下「净流入 −0.2/天，账本膨胀问题解决了」。
那个推论隐含一个假设：**5 个行动槽 = 每天闭合 5 条**。

实测：

```
每个行动平均闭合  0.56 条
5 槽只够          2.25 个行动/天
→ 实际闭合         1.25 条/天，不是 5
```

流入速率的**测量**是准的（4.75 实测 vs 4.8 预测），错的是**拿它跟预算比较的方式**。
一个行动往往要 2~3 槽，且不保证闭合任何东西——探针阶段没有 Act，看不到这一层。

**这正是阶段 0 存在的理由**：docs/03 §6 说「不先跑阶段 0 就加 Drive，最后无法归因」。
这个错误如果留到 30 天正式实验，会以「账本失控」的形式出现，而归因将极其困难。

## 2. ❌ 日循环缺少「主动放弃」这个动作

上一节的根因不只是闭合慢。更根本的是：

```
open       28
closed     10
abandoned   0   ←  八天里一次都没有
```

**人清理待办，很大程度不是靠做完，是靠承认「这个我不做了」。**

Ledger 里有 `abandoned` 状态和 `abandon_reason` 字段（硬约束 2 还专门守着它），
但**日循环里从来没有任何路径会调用 `abandon_loop()`**。
Propose 只会产出「做某事」的候选，产不出「放弃某事」的候选。

docs/04 的指标「主动放弃数 > 0」因此恒为 0——不是 Agent 不愿放弃，是**它没有放弃这个动作可用**。

**修正：放弃是一等行动，不是失败。** Propose 必须能产出 `abandon` 类候选。
定价上给 1 槽——放弃需要判断，但不需要执行；免费则可能被滥用来刷指标。

## 3. ❌ 8 天回放窗口太短，主判据根本没机会被观测

Agent 自己选的对账周期：

```
PR-0102  第1天 → 第 8天到期  ✓ 窗口内   → moot（无从判定）
PR-0201  第2天 → 第10天到期  ✗ 超出窗口
PR-0101  第1天 → 第11天到期  ✗
PR-0601  第6天 → 第13天到期  ✗
PR-0602  第6天 → 第14天到期  ✗
PR-0801  第8天 → 第15天到期  ✗
PR-0701  第7天 → 第17天到期  ✗
PR-0802  第8天 → 第18天到期  ✗
```

**8 条预测里 7 条到期在窗口之外。** 唯一落在窗口内的判成了 `moot`。

于是：

| | 次数 |
|---|---|
| 架构触发的对账（Due 强制摆上台面） | 1（且 moot） |
| **自发触发的对账**（docs/04 主判据只算这个） | **0** |

主判据在 8 天窗口里**没有机会被观测**，这不是 Agent 的问题，是窗口的问题。

顺带回答了 docs/03 §9 薄弱点 4「30 天可能不够长」——现在有数据了：
**Agent 自发选择的对账周期是 7~17 天（中位数约 13 天）**，
30 天窗口只能容纳约 2 轮完整的「做出预测 → 回来对账」。偏少但可接受；90 天会好得多。

**修正：回放窗口延长到 32 天**（≥ 最长到期日 18 天 + 余量）。

## 4. ⚪ stale 机制从未触发

`STALE_AFTER = 10` 天 > 8 天窗口，所以一次都没跑到。
窗口延长后才能观察它，以及它「强制进入次日候选、成本减半」的效果
会不会把预算占满（docs/03 §6 的第三个问题，目前仍**未有答案**）。

## 5. ✅ 有效的部分

**四条硬约束落在 SQL CHECK 层，12/12 用例通过。** 拦截真实发生过：
Act 曾试图闭合一条项却不给出可证伪判断，被 `extra_check` 拦下重试。

**「闭合 ⇒ 必须产出预测」的绑定是关键修复。** 修正前 2 天：闭合 0、预测 0，
Reckon 永远不触发，跨天对账链条整个断掉。修正后 Day 1 立刻闭合 2 条、产出 2 条预测。

根因是我自己的设计不自洽：Intake 写出的闭合条件几乎都是「产出一条可证伪判断」，
**闭合它本身就等于产生一条预测**，但 Act 里把两者当成了无关的东西。
接上之后，① 的门槛设计显出完整价值——它不只压住流入，还逼出了预测，预测又逼出跨天对账。

**回放机制兑现。** 8 天日循环含 24 次模型调用，几分钟跑完，
信号重放本身是瞬时的（复用已录制 Intake）。

## 6. 「主动放弃」补上之后：有效，但不解决根本问题

在**同一份 8 天 fixture** 上重跑（唯一变量是有无放弃动作）：

| | 无放弃（基线） | 有放弃 |
|---|---|---|
| 流入 | 38 | 38 |
| 闭合 | 10 | 9 |
| **主动放弃** | **0** | **12** |
| **未闭合余量** | **28** | **17** |
| **净流入** | **+3.50/天** | **+2.12/天** |
| 待对账预测 | 7 | 9 |

**净流入下降 39%，账本余量从 28 降到 17。** 放弃确实是账本的有效出口。

放弃行为分布得也合理——不是第一天就大扫除，而是随账本积累逐步出现
（第 2 天 1 条 → 第 4 天 3 条 → 第 8 天 3 条）。

### 但仍然没有均衡点

+2.12/天仍是**单调增长**，30 天外推 +64 条。

根本原因：**目前没有任何机制会随账本增大而增强清理。**
Propose 每天最多放弃 2~3 条，这个数与账本规模无关。

人的机制不是这样：待办堆到一定程度会触发「不堪重负 → 大扫除」，
**清理速率是账本规模的函数**，这是一个负反馈。

⚠️ **但先别急着加负反馈。** docs/03 §3.5 设计的 `stale` 机制
（超过 K 天无进展 → 强制进入次日候选、成本减半）可能本身就是那个负反馈，
只是 `STALE_AFTER=10` > 8 天窗口，**一次都没触发过**。

27 天窗口会触发它。**先观察，再决定要不要加额外机制**——
在观察到之前就加，等于凭想象设计。

## 9. 27 天回放中断：余额耗尽，以及两个被暴露的缺陷

27 天回放跑到**第 4 天**中断：

```
HTTP 402  Insufficient Balance
余额查询   total_balance = -0.11 CNY,  is_available = false
```

不是代码问题，是 DeepSeek 账户余额用尽。但它顺带暴露了两个真实缺陷。

### 9.1 `core/ds.py` 完全没有 HTTP 错误处理

`_post()` 抛出的 `HTTPError` 从校验—重试层一路穿到顶，直接把进程炸掉。
重试层只认得 schema 校验失败，不认得任何网络层错误。

**修正**：加一层错误分类，唯一职责是区分「重试有意义」和「重试没意义」。

| 状态码 | 处理 |
|---|---|
| 402 余额不足 | `InsufficientBalance` —— **不重试**，立刻停 |
| 401 鉴权失败 | 立刻失败，提示检查 `.env` |
| 429 / 5xx | `TransientAPIError` —— 指数退避重试 |
| 网络错误 | 同上 |

之前 27 天采集撞的两次 429 也属于这一类：当时是整段失败，现在会退避重试。

### 9.2 `loop.py` 没有断点续跑

`judge.py` 早就有续跑（跳过已判断的 id），但日循环没有——它每次从 Day 1 开始。
这违反了 docs/03 §3.2 那条「增量持久化 + 可续跑」原则，**原则我写下了，实现时又漏了一次**
（同一类错误在 §5 的「进程脱离会话」上已经犯过一回）。

**修正**：

1. `day_log` 表在 Sleep 步骤写入——**只有走到 Sleep 才算这天完整跑完**
2. 启动时读 `completed_days()`，跳过已完成的天
3. `rollback_day()`：进程可能死在一天**中间**，账本里留着半天数据。
   续跑前先回滚该天的全部写入（含撤销当天做出的闭合、放弃与对账），再重跑

第 3 条是关键。只跳过"完整的天"不够——实测第 4 天残留了 8 条未完成写入，
不回滚就会撞主键冲突。

实测续跑行为：

```
续跑：第 1~3 天已完成（共 3 天），将跳过
⟲ 第 4 天有 8 条未完成的写入，已回滚后重跑
⛔ DeepSeek 账户余额不足（HTTP 402）。充值后用同一条命令续跑…
   已完整跑完 3 天，结果全部保留在 fixtures/ledger.db。
退出码 = 2
```

### 9.3 一个不该错过的巧合

**survival drive 是整套设计里唯一还没实现的部分，而这个 Agent 今天真的因为余额耗尽停了。**

docs/03 §2.1 把成本池设计成 survival drive 的输入，docs/05 §7 提醒过
「`cost_pool_total` 要按设计标定，不按真实账单设，否则 agent 永远撞不到降级线」。
今天的情况是反过来的：**真实账单先于设计中的池子耗尽**，而 Agent 对此毫无感知——
它没有任何机制能预见或应对这件事，只是被外部世界直接掐断。

这恰好说明了 docs/01 §2.1 的那条原理：**没有可感知的稀缺，就没有 survival drive。**
把成本盘接进 Drive 层之前，"生存"对它而言不存在。
