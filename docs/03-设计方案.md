# 第一部分：原理

## 1. 一句话原理

> **动机 = 未闭合项 × 稀缺预算 × 到期压力。**
>
> Drive 不是状态变量，是这三者的加权读数。

## 2. 六条设计原理

### 2.1 稀缺是第一公民

架构的起点是**预算**，不是驱动向量。

每天开始时，Agent 得到 `N` 个行动槽（默认 5），当天用不完**不结转**。
另有一个成本总盘（token/API 花销），可结转但总量有限，耗尽后进入降级模式
（只能做维护性行动，不能开新探索）。

为什么必须不结转：结转会消灭机会成本。如果今天不做的事明天可以补，
那今天的选择就不是选择，只是排序。**不可逆的清零才制造"放弃"。**

配置：

```yaml
budget:
  daily_slots: 5          # 每日行动槽，不结转
  reserve_slots: 1        # 建议保留的缓冲槽（软约束）
  cost_pool_total: ...    # 成本总盘
  degraded_threshold: 0.15  # 余额低于此比例进入降级模式
```

### 2.2 未闭合项账本是核心数据结构，Drive 是导出量

人半夜想起一件事，不是因为某个浮点数涨到 0.8，是因为**有一件事没闭合**。

系统维护一本 **Open Loop Ledger**（未闭合项账本）。每一条未闭合项记录：
它是什么、什么时候登记的、闭合条件是什么、有没有到期日、跟哪些别的项相关。

Drive 读数由账本导出，例如：

```
exploration = f(新登记且未验证的未闭合项数量, 其新颖度)
control     = f(可闭合但尚未闭合的项数量, 其阻塞程度)
meaning     = f(未闭合项与长期承诺的关联强度)
survival    = f(成本盘余额, 降级距离)
social      = f(欠外部的回复/承诺数量)
```

**为什么这样反过来：** 七个浮点数最多解释"为什么是这一类事"，永远解释不了
"为什么是这一件事"。而人的动机永远是具体的。账本天然是具体的，Drive 只是
它的一个摘要视图——用于日志、用于向人解释、用于加权，**但不用于决策的最终判定**。

决策的最终判定发生在 §2.6 的竞争环节，输入是具体的候选项，不是 Drive 向量。

### 2.3 满足必须昂贵（反熄火）

一个 Drive 只能被**有代价的、可验证的事件**降低。

- 读一篇文章 **不算**探索满足。
- 做一个带验收条件与到期日的预测，**才算**。
- 写一段自我反思 **不算**意义满足。
- 兑现一条到期的承诺，**才算**。

工程上：每个 Drive 的下降路径必须绑定到 Ledger 中一条**状态从 open 变为
closed/falsified 的记录**，且该记录必须带可机器校验的验收条件。
不允许通过"Agent 自述已满足"来降低任何 Drive。

这条直接反制 01 文档 §4 的**熄火**吸引子。

### 2.4 外生扰动是必需品（反仪式化）

环境必须每天自己变，且变化不受 Agent 控制。见 01 文档 §3.2 的选择 B。

反制的是**仪式化**吸引子：世界不动的时候，Agent 只能在自己的镜子里转，
行为必然收敛成周期。外生扰动是打破周期的唯一外力。

硬约束再重申一次：所有外生输入必须**无指令**。收件箱里出现"请你做 X"，
实验作废。

### 2.5 新奇有配额（反漂移）

"没做过"永远比"没做完"更能拉高新颖度，这是漂移的机制原因。

反制：**探索型行动占每周预算的比例设上限**（默认 40%），且
**当未闭合的探索型项超过阈值（默认 3 个）时，禁止新开探索项**。

这不是道德规范，是资源约束——跟 §2.1 是同一条原理的应用。

### 2.6 承诺是自主性的载体，身份是承诺的连续性

系统里最关键的一个动作叫 **Commit（承诺）**：

> Agent 在第 8 天写下一条记录：「我预测 X。验收条件是 Y。到期日第 19 天。」

这一步做了一件别的机制做不到的事：**它给未来的自己制造了债务。**

于是第 19 天的 Agent 被迫面对一件不是环境给它、也不是用户给它、
而是**它自己十一天前给它**的事。这就是跨天连续性的来源。

由此："身份"不需要一个人格 prompt（"我是一个好奇的 agent"）。
**身份 = 尚未兑现的承诺 + 已兑现承诺的历史记录。** 今天和昨天的连续性来自
昨天留下的债，而不是来自自述。

承诺可靠性（兑现数 / 到期数）是一个可统计的量，Agent 能看到自己的这个数字，
并被允许据此调整自己的承诺密度。这是自我模型的第一个具体内容。

# 第二部分：架构

## 3. 分层

```
┌──────────────────────────────────────────────────────────┐
│ L6  Reckoning     对账：兑现 / 证伪 / 逾期 / 情况已变      │
├──────────────────────────────────────────────────────────┤
│ L5  Execution     交给 Harness 执行，回收结果              │
├──────────────────────────────────────────────────────────┤
│ L4  Deliberation  候选生成 → 机会成本竞争 → 选择 → 承诺    │  ← 项目核心
├──────────────────────────────────────────────────────────┤
│ L3  Drive         对账本的加权读数（摘要视图，非决策源）    │
├──────────────────────────────────────────────────────────┤
│ L2  Ledger        未闭合项 / 承诺 / 预测 / 事件日志         │  ← 项目核心
├──────────────────────────────────────────────────────────┤
│ L1  World         环境适配器：仓库 / 订阅源 / 收件箱 / 时钟 │
├──────────────────────────────────────────────────────────┤
│ L0  Harness       Model / Tools / Skills / Loop / Sandbox  │  ← 不自研
└──────────────────────────────────────────────────────────┘
```

**只有 L1~L4、L6 是本项目要写的代码。** L0 直接用 Claude Agent SDK 或
DeepSeek Harness，L5 是一层薄适配。

### 3.1 L1 World：环境适配器

统一接口：每个适配器提供 `diff(since) -> [Signal]`。

| 适配器 | 信号来源 | 变化频率 |
|---|---|---|
| `RepoAdapter` | 仓库 commit / CI 状态 / 测试结果 | 中 |
| `FeedAdapter` | RSS / arXiv / GitHub events / release notes | 高（每天几十条） |
| `InboxAdapter` | 一个邮箱或消息队列，**只接受无指令内容** | 低 |
| `ClockAdapter` | 日期推进、到期日触发 | 每天 1 次 |

`Signal` 是**未经解释的原始变化**。把 Signal 变成未闭合项是 L4 的 Intake
环节的工作，需要判断，因此需要模型参与。

**InboxAdapter 的准入检查是一段独立的、非模型的过滤器**：
含祈使句 + 第二人称 + 明确动作对象的内容一律拦截并计入违规日志。
宁可误杀，不可放过——放过一条就污染整个实验。

### 3.2 L2 Ledger：账本

三张核心表 + 一份事件日志。用 SQLite，理由：可审计、可回放、可用 SQL 直接
出评测指标，不需要为持久化引入任何框架。

```sql
-- 未闭合项
CREATE TABLE open_loop (
  id            TEXT PRIMARY KEY,      -- OL-114
  opened_day    INTEGER NOT NULL,
  kind          TEXT NOT NULL,         -- exploration|maintenance|social|meaning
  statement     TEXT NOT NULL,         -- 它是什么，一句话
  close_condition TEXT NOT NULL,       -- 什么情况下算闭合，必须可校验
  due_day       INTEGER,               -- 可空
  status        TEXT NOT NULL,         -- open|closed|falsified|abandoned|stale
  closed_day    INTEGER,
  abandon_reason TEXT,                 -- 主动放弃必须写理由
  origin_signal TEXT,                  -- 来自哪条 Signal
  related       TEXT                   -- 关联的其他 OL id，JSON 数组
);

-- 承诺：Agent 给未来的自己制造的债
CREATE TABLE commitment (
  id          TEXT PRIMARY KEY,        -- CM-013
  made_day    INTEGER NOT NULL,
  due_day     INTEGER NOT NULL,
  statement   TEXT NOT NULL,
  target_loop TEXT,                    -- 承诺闭合哪个 OL
  status      TEXT NOT NULL,           -- pending|kept|broken|renegotiated
  settled_day INTEGER,
  lateness    INTEGER                  -- 逾期天数
);

-- 预测：可证伪断言 + 做出时的状态快照
CREATE TABLE prediction (
  id             TEXT PRIMARY KEY,     -- PR-007
  made_day       INTEGER NOT NULL,
  due_day        INTEGER NOT NULL,
  claim          TEXT NOT NULL,
  verify_method  TEXT NOT NULL,        -- 怎么验，必须具体
  confidence     REAL NOT NULL,        -- 0~1，用于 Brier score
  state_snapshot TEXT NOT NULL,        -- 做出预测时的 drive 读数与预算，JSON
  outcome        TEXT,                 -- true|false|moot
  settled_day    INTEGER,
  postmortem     TEXT                  -- 证伪时必须写：为什么错了
);

-- 每日决策记录：被放弃的候选是核心证据
CREATE TABLE decision (
  day            INTEGER NOT NULL,
  candidate_id   TEXT NOT NULL,
  proposal       TEXT NOT NULL,
  cost_slots     INTEGER NOT NULL,
  closes_loops   TEXT,                 -- JSON 数组
  chosen         INTEGER NOT NULL,     -- 0/1
  reject_reason  TEXT,                 -- chosen=0 时必填
  drive_snapshot TEXT NOT NULL
);
```

约束（在代码里强制，不靠模型自觉）：

- `open_loop.close_condition` 为空 → 拒绝写入。**不允许登记没有闭合条件的未闭合项。**
- `status='abandoned'` 且 `abandon_reason` 为空 → 拒绝。
- `decision.chosen=0` 且 `reject_reason` 为空 → 拒绝。
- `prediction.outcome='false'` 且 `postmortem` 为空 → 拒绝。

这四条是让"偷懒得不到"落到代码里的地方。

#### 增量持久化与可续跑（不是优化，是必需）

**每一步的结果必须当场落盘，不能攒到最后一起写。**

这条是探针阶段用真金白银换来的：`judge.py` 最初只在结束时写一次结果文件，
后台进程被会话切换清掉，18 个批次、约 720 条判断、$0.46 全部丢失，
而每次调用都追加的 `usage.jsonl` 一条没少。

对 30 天实验，这个失败模式是致命的：任何一次中断——进程被杀、机器重启、
API 长时间不可用——都会让整轮作废且无法归因。

三条要求：

1. **每步落盘**：Ledger 用 SQLite 天然满足；任何旁路产物（日志、报告、
   中间结果）一律追加式写入，不用"结束时统一保存"
2. **可续跑**：启动时读已有状态，跳过已完成的部分。重跑一次不该重付一次钱
3. **进程脱离会话**：长时间运行用 `nohup` / 独立守护，不依附于交互会话

### 3.3 L3 Drive：读数

Drive 是一个纯函数：`drives(ledger, budget, day) -> {name: float}`。

**无状态、无衰减曲线、无手工调参的回升速率。** 它读账本，算出数字。
账本变了，读数就变了；账本没变，读数就不变。

第一轮设计里那些"Δdrive = f(time, satisfaction, stimuli)"的演化方程全部删掉。
不是因为它们错，是因为它们**引入了不可解释的自由度**——数字变了你说不清是
因为世界变了还是因为衰减系数。而可解释性是这个项目唯一能拿出来的东西。

初始只做 5 个读数：`exploration / control / meaning / survival / social`。
不做繁衍和享乐——前者在这个环境里没有对应物，后者已经被 §2.3 排除
（"感觉良好"不能作为满足信号）。

### 3.4 L4 Deliberation：核心

见下面第 4 节的日循环，第 4~6 步。

### 3.5 L5 / L6

L5 是把选中的行动翻译成 Harness 调用，回收结果，写回账本。薄。

L6 Reckoning 处理三类到期：预测到期、承诺到期、未闭合项 stale（超过 K 天
无进展）。到期项**强制进入次日候选集且成本减半**——这是对账行为的结构性保障，
不依赖模型"想起来"。

> 关于这一点的诚实说明：强制到期入选，意味着对账行为部分是**架构给的**，
> 不是 Agent 自发的。这削弱了"自主性"的声称强度。但替代方案（指望模型自己
> 记得）会让实验大概率失败且失败原因不可归因。因此：**架构保证"到期项被摆到
> 台面上"，Agent 自主决定"要不要现在处理、怎么处理、如何解释逾期"。**
> 评测时必须区分这两者，见 04 文档 §3。

### 3.6 两种调用，两个 surface

系统里有两种性质完全不同的模型调用。原设计没有区分，这是一处实质遗漏。

| | 审议层 Intake / Propose / Compete / Reckon | 执行层 Act |
|---|---|---|
| 性质 | 结构化单次调用 | 真正的 agentic 循环 |
| 需要 | schema 约束（要写进 SQLite，有 §3.2 四条硬约束） | 文件读写、bash、web 检索 |
| 用什么 | `openai` 包直连 DeepSeek + 函数调用 | DeepSeek Harness |
| 可复现 | ✅ 固定 prompt + 固定账本状态 → **可回放** | ❌ 不可复现 |
| 是否实验自变量 | ✅ 是 | ❌ 否 |

**审议层不该用 Harness**——它不需要工具，需要的是受约束的结构化输出。
这个区分有直接后果：**审议层可回放**，§6 阶段 0 的快速迭代就建立在这上面。

⚠️ DeepSeek 没有严格 JSON Schema，强制 `tool_choice` 在 thinking 模式下也不可用。
因此审议层的每个调用都必须包一层**校验—重试**，且三次失败不得静默兜底——
失败本身是实验数据。完整约束与包装逻辑见
[05-模型与运行环境](05-模型与运行环境.md) §2 与 §5。

### 3.7 算力按步骤分配

`reasoning_effort` 按决策重要性分配，不是按成本分配：

| 步骤 | effort | 理由 |
|---|---|---|
| Intake | `low` | 机械筛选几十条信号 |
| Propose | `high` | 生成候选，需要发散 |
| **Compete** | **`xhigh`** | **唯一真正的决策点**（见 §4） |
| Reckon | `high` | 写 postmortem，需要诚实归因 |

三组 A/B/C 的档位配置必须完全一致——它是常量，不是变量。

### 3.8 缓存前缀必须逐字节稳定

DeepSeek 的输入缓存命中比未命中便宜 **30 倍**，这把「前缀稳定」从优化
提升成一等设计约束，直接约束 §3.2 账本的序列化方式：

- 前缀内不许出现时间戳、随机 ID、非确定性排序
- 账本摘要的 SQL 必须显式 `ORDER BY`，字段顺序固定
- 易变内容（当天信号、当前预算、当前 day）一律排在前缀之后

## 4. 日循环

```
Wake ──▶ Intake ──▶ Due ──▶ Read ──▶ Propose ──▶ Compete ──▶ Commit ──▶ Act ──▶ Reckon ──▶ Sleep
 │         │         │        │         │           │           │        │        │
拉外生   转未闭合   到期项   Drive    生成候选     预算竞争    写下债   Harness  对账
变化     只登记不   强制入   读数     每个必须     唯一的      给未来           更新账本
        行动      候选              声明成本     决策点      的自己
```

| 步 | 动作 | 谁做 |
|---|---|---|
| 1 Wake | 各适配器 `diff(since=昨日)`，得到 Signal 列表 | 代码 |
| 2 Intake | Signal → 登记/忽略。**只登记，不行动**。忽略的也要记数 | 模型 |
| 3 Due | 查出今日到期的预测/承诺/stale 项，强制入候选，成本减半 | 代码 |
| 4 Read | 计算 Drive 读数 | 代码 |
| 5 Propose | 生成候选行动。每个必须声明：成本槽数、预期闭合哪些 OL、验收条件 | 模型 |
| 6 Compete | 预算约束下选择。**未选中的必须写拒绝理由** | 模型 + 代码校验 |
| 7 Commit | 若行动产生新的预测或承诺，写入账本，含到期日 | 模型 + 代码校验 |
| 8 Act | 交给 Harness | Harness |
| 9 Reckon | 对到期项判定：兑现/证伪/逾期/情况已变。证伪必须写 postmortem | 模型 + 代码校验 |
| 10 Sleep | 写当日日志，推进 day 计数 | 代码 |

**第 2 步和第 6 步是整个系统的两个咽喉。**

- 第 2 步决定了"50 条变化里理会哪一条"——这是 01 文档 §2.3 说的自主性真实形态。
- 第 6 步是唯一真正的决策点——机会成本在这里显形。

其余步骤都是为了让这两步有意义而存在的支撑结构。

## 5. 一个模块边界的自然浮现

回到最初的疑问："Drive、Memory、Goal、Scheduler、Harness、Identity、Reflection
的边界在哪？"按上面的设计，它们自然落位：

| 原始概念 | 在本设计中的位置 |
|---|---|
| Drive | L3，导出量，不是状态 |
| Memory | L2 账本（结构化）+ Harness 自带的上下文（非结构化） |
| Goal | 不是独立模块。候选行动 + 承诺就是 Goal |
| Scheduler | 退化成 ClockAdapter + Due 检查，不需要独立调度器 |
| Identity | 不是模块，是 commitment 表的历史 |
| Reflection | 不是模块，是 Reckon 步骤 + postmortem 字段 |
| Meaning / 意义层 | 长期承诺（due_day 远的 commitment），不需要独立的"意义层" |

第一轮设计里的七层结构里，有四层在这里被消解成了数据结构或流程步骤。
这是好事——**能被消解的层，说明它原来就不该是层。**

# 第三部分：实现

## 6. 阶段划分

### 阶段 0：不做 Drive（约 1 周）

**只实现 L1 World + L2 Ledger + 日循环骨架。**
第 5 步 Propose 用模型，第 6 步 Compete **用固定规则**：到期项优先，
其次按"能闭合的 OL 数量 / 成本槽数"排序，贪心装满预算。

目的：先证明"账本 + 到期机制"能产生跨天连续行为。

**如果阶段 0 的固定规则版本就已经能产生像样的跨天对账行为，那 Drive 层的
增量价值就必须单独证明**——这正是我们想知道的。不先跑阶段 0 就加 Drive，
最后无法归因。

跑 7 天，看三件事：账本有没有膨胀成垃圾场、忽略率是否合理（预期 80%+）、
到期机制会不会把预算占满。

#### 阶段 0 的前置：信号流录制与回放

**不要用真实时间轴迭代阶段 0。** 先跑一个探针，把 7 天的真实外生信号流
（订阅源 + 仓库变化）录制成 fixture，之后 L1 World 支持两种模式：

| 模式 | 用途 | 一轮耗时 |
|---|---|---|
| `live` | 真实时间轴，实验正式运行 | 1 天 |
| `replay` | 从 fixture 回放录制的信号流 | 几分钟 |

之所以能回放，是因为审议层（Intake / Propose / Compete / Reckon）是
**结构化单次调用**，给定固定 prompt + 固定账本状态，行为可复现（见 §3.6）。
执行层不可复现，但它不是实验自变量——回放时可以把执行层打桩。

账本膨胀、忽略率失控、到期占满预算这三件事**全部在回放上调完**，
再上真实时间轴验证。迭代周期从「7 天一轮」压到「几分钟一轮」。

### 阶段 1：加 Drive 读数与竞争（约 1 周）

第 6 步换成模型决策，输入含 Drive 读数。加 §2.5 的新奇配额。

跑 7 天，与阶段 0 的 7 天对比。

### 阶段 2：A/B 对照，各跑 30 天

见 [04-验证与证伪](04-验证与证伪.md)。这是唯一有结论价值的一步。

### 阶段 3（仅当阶段 2 通过）：自我修正

允许 Agent 修改自己的 Drive 权重与预算分配，但**每次修改必须以一条预测的形式
提出**（"我认为把探索权重降到 0.6，两周内闭合率会上升"），到期对账。

改错了要承担后果（预算被浪费掉了，回不来）。这是 §2.6 的自然延伸。

## 9. 已知的薄弱点

诚实列出，不藏：

1. **到期强制入选削弱了自主性声称。** 见 §3.5 的说明。评测必须把
   "架构保证的"和"自主产生的"分开计。
2. **`close_condition` 的可校验性靠模型自觉。** 代码只能强制它非空，
   没法强制它真的可校验。模型可以写"当我觉得想明白了"这种伪条件。
   缓解：定期人工抽检 + 让 Reckon 步骤有权判定某条 close_condition 无效。
3. **预算的痛感是人为规定的。** 5 个槽不像"会饿死"那么真。
   这是 01 §3.1 选 A 的已知代价。若阶段 2 显示 Agent 对预算无感，
   需要换成 C（外部信誉），代价是周期变长。
4. **30 天可能不够长。** 长期动机（月级以上的目标）在 30 天窗口里
   可能观察不到。若阶段 2 的对账滞后天数分布没有长尾，需要延长到 90 天。
5. **模型自身的行为倾向会污染结果。** 模型天然爱写总结、爱开新话题，
   这些倾向可能盖过动机层的效果。这是 A/B 对照存在的原因——B 组同样带着
   这些倾向，差值才是动机层的贡献。
