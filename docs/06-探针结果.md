## 3. 五个对设计有后果的发现

### 3.1 ⚠️ Intake 的判据写错了，会撑爆账本

这是最重要的一条。

```
每天理会 12.25 条  →  登记为未闭合项
每天预算  5 槽    →  能行动的上限
```

**净流入约 7 条/天，30 天累积 210 条未闭合项。** 这正是 docs/03 §6 阶段 0
要盯的「账本膨胀成垃圾场」，现在有了确切数字。

根因不在预算，在判据。探针问模型的是：

> 这条**与我的关切有没有关系**？

但阶段 0 需要的是更高的门槛：

> 这条**值不值得成为一条带闭合条件的未闭合项**？

**相关 ≠ 值得追踪。** 一篇论文与动机机制有关，不等于它值得占用账本、
等待闭合、参与每天的预算竞争。修正 Intake 判据后，预期从 12/天 压到 3–6/天，
与 5 槽预算才匹配得上。

配套：docs/03 §3.5 的 stale 机制（超过 K 天无进展）必须与流入率联合标定，
**使「登记速率 ≈ 闭合速率 + stale/放弃速率」**，否则账本无界增长。

### 3.2 ⚠️ 反漂移配额被实测证实是必需的

被理会的 98 条，kind 分布：

```
exploration  68  (69%)
meaning      21  (21%)
maintenance   9  ( 9%)
```

**近七成是探索型。** 如果不加约束，账本会迅速被探索项塞满——
这正是 docs/01 §4 的**漂移吸引子**：30 个开头、0 个完成。

docs/03 §2.5 的两条约束（探索占每周预算 ≤40%、未闭合探索项 >3 个时禁开新的）
原本是推理出来的，现在有实测支撑：**不加约束，探索会以 7:2:1 的比例碾压其他驱动。**

### 3.3 ⚠️ schema 校验拦不住引用完整性错误

1068 条信号，有效判断 1063 条（覆盖率 99.53%）。差额来自一个 schema 校验
**完全无法发现**的错误：模型返回了 4 个不存在的 signal id。

```
282662ff012   ← 真实 d282662ff012    丢了首字符
9653988daad   ← 真实 d9653988daad    丢了首字符
28ab17d0031   ← 真实 c28ab17d0031    丢了首字符
081b57e509a2  ← 真实 081b57e509a6    末位 6 写成 2
```

不是凭空捏造，是**转写错误**——内容判断全部正确，只有标识符抄错。
但 schema 只管「id 是不是字符串」，这类错误一路通过。

**两条修正：**

1. **引用完整性必须单独校验**：凡是引用既有对象的字段（signal id、OL id、
   commitment id），必须检查它确实存在于输入集合中。这要加进 `ds.py` 的校验层，
   也要加进 docs/03 §3.2 的硬约束。
2. **改 ID 方案**：12 位十六进制天生易抄错。批内改用短序号（`S01`…`S40`），
   转写错误率大幅下降，且越界立刻可查。

对阶段 0 这条是硬伤：如果 Compete 或 Reckon 编错一个 OL id，
就会写下一条指向不存在的未闭合项的决策记录。

### 3.4 arxiv/cs.LG 是纯噪声，建议摘掉

142 条、0 条相关。且它只是被 429 截断后的部分——完整 cs.LG 会是最大的单一来源。

摘掉是否会让实验变简单？**不会。** 去掉 cs.LG 后忽略率从 90.8% 变成 89.4%，
几乎不动——真正提供负样本的是 cs.AI（811 条里 731 条不相关）。
cs.LG 只贡献成本，不贡献辨别力。

保留的唯一理由是把它当作对照噪声源。**建议摘掉**，理由是它可能占到总量的 40%
却零产出；若要保留噪声对照，用一个体量小得多的无关分类即可。

### 3.5 缓存命中率随批次上升

首次 120 条试跑命中率 28.3%，全量 1068 条跑完 **51.3%**。
稳定的系统提示前缀被反复命中，批次越多摊得越薄。

阶段 0 的账本摘要前缀比这里的系统提示大得多，命中率应更高。
但这条要持续盯——docs/03 §3.8 的「前缀逐字节稳定」一旦被破坏，
成本会静默上涨 30 倍且不会报错。

## 4. 成本实测

| 项 | 值 |
|---|---|
| 总调用 | 46 次（含丢失重跑的 18 次） |
| 缓存命中率 | 51.3% |
| **推理占输出 token** | **69%** |
| 累计成本 | **$1.105** |
| 单条信号成本 | 约 $0.0008 |

推理占输出近七成，坐实 docs/05 §3 的结论：`max_tokens` 必须给足，
不够时 `content` 静默返回空且不报错。

外推 30 天 × 3 组的 Intake 层：约 **$10**（离峰减半约 $5）。
成本不构成约束。

## 5. 回填 docs/04 的指标基线

| 指标 | 原预期 | 实测 | 结论 |
|---|---|---|---|
| Intake 忽略率 | 70%~95% | **90.8%** | ✅ 区间正确，无需调整 |
| 判断覆盖率 | 未定义 | 99.53% | 新增指标，及格线 ≥99% |
| 批次失败率 | 未定义 | 0/24 | 校验—重试层有效 |

**新增两条必测项**（原 docs/04 缺失）：

- **引用完整性错误率**：模型返回的 id 中不存在于输入集合的比例。及格线 0（改 ID 方案后）
- **每日登记流入率 vs 预算**：登记速率必须 ≈ 闭合速率 + stale 速率，否则账本无界增长

## 6. 过程中花钱买到的两个教训

**增量持久化不是优化。** `judge.py` 最初只在结束时落盘一次，后台进程被会话切换
清掉，18 批、约 720 条判断、$0.46 全丢；而每次调用都追加的 `usage.jsonl` 一条没少。
已升格为设计原则（docs/03 §3.2）：每步落盘、可续跑、进程脱离会话。

**`source activate` 会被 shell alias 静默架空。** 本机 zsh 把 `python` alias 到
`python3.12`，alias 优先级高于 activate 改的 PATH，实际跑在全局解释器上。
全局恰好装了同名包时**不会报错**。一律用 `.venv/bin/python` 显式调用。

这是回放机制的第一次实际使用，没有重新采集数据。

| 批次失败 | 0 | 0 | ✅ |

### 7.2 ✅ 修正① 有效：账本膨胀问题解决

判据从「是否相关」改成「值不值得成为一条带闭合条件的未闭合项」，
并把 `close_condition` 变成**强制门槛**——写不出可检验的闭合条件就不该登记。

**日均登记从 12.25 降到 4.8，与 5 槽预算基本持平（净流入 −0.2/天）。**
8 天里 6 天落在 3~6 的目标区间。

```
2026-08-18   100 条 → 登记 4  ✅      2026-08-22   111 条 → 登记 4  ✅
2026-08-19   141 条 → 登记 6  ✅      2026-08-23   125 条 → 登记 5  ✅
2026-08-20   150 条 → 登记 4  ✅      2026-08-24   215 条 → 登记 6  ✅
2026-08-21   165 条 → 登记 8  ⚠️高    2026-08-25    61 条 → 登记 1  ⚠️低
```

关键设计选择：**用闭合条件当门槛，而不是设一个"每天最多 6 条"的配额。**
配额测的是指令遵循，闭合条件测的是这条信号到底有没有实质内容可追踪。

产出的闭合条件确实可检验，不是"读完它"那种：

> 「把其自我进化审计发现与我的连续性机制逐条对比，产出一条可证伪判断：
> 我的技能/记忆进化路径是否存在同类『能力增益伴随正确行为丢失』的漂移」

> 「将其内存管道故障定位协议应用到我自己的跨会话记忆设计上，
> 产出明确结论：我的记忆管道存在/不存在同类未定位的失效点」

副作用：v2 判据更明确（二值判断），模型反而少绕弯子——
推理占输出从 69% 降到 53%，每条信号的输出 token 从 134 降到 83。

### 7.3 ✅ 修正② 有效：引用完整性错误归零

批内短序号（`S01`…`S50`）替代 12 位十六进制，配合 `ds.py` 新增的
`extra_check` 业务校验钩子（schema 管不了的约束在这里查）。

**幽灵编号 4 → 0，漏判 5 → 0，覆盖率 100%。** 转写错误的成因被直接消除。

`extra_check` 同时管了结构一致性：登记则必须有 ≥12 字的 close_condition 且
kind ≠ none；未登记则 kind 必须为 none 且闭合条件为空。这些都是 schema
表达不了、又必须强制的约束，阶段 0 的 Compete / Reckon 会复用同一个钩子。

### 7.4 ❌ exploration 偏斜没有被解决

**71%，比 v1 的 69% 还略高。**

判据变严只减少了**总量**，没有改变**构成**。这证明 docs/03 §2.5 的反漂移配额
是一条**独立的、不可被 Intake 判据替代的约束**——必须在 Compete 阶段执行。

### 7.5 ⚠️ 新发现：当前 World 只有"进来的"，没有"我的"

v2 的 kind 分布：

```
exploration  27
meaning      11
maintenance   0    ← 归零
social        0    ← 一直是 0
```

v1 有 9 条 maintenance，v2 严格化后归零。原因不是判据太严，是
**世界里根本没有 maintenance 信号源**：探针只接了 arXiv / GitHub 检索 / RSS，
全是"外部世界出现的新东西"，没有一条是"我自己的东西坏了"。
v1 那 9 条是从论文里牵强判出来的，收紧后自然消失。

docs/03 §3.1 设计了 `RepoAdapter`（仓库 commit / CI / 测试）与 `InboxAdapter`，
但探针阶段两者都没实现——因为 Agent 还没有自己可写的沙盒仓库，也没有收件箱。

**后果是叠加的**：

- maintenance 恰恰是最容易产生**明确闭合条件**的未闭合项（CI 挂了 → 修好即闭合）
- 缺了它，账本 100% 由 exploration + meaning 构成
- 这与 §7.4 的探索偏斜叠加，把漂移风险推得更高

**结论：阶段 0 必须先给 Agent 一个自己的沙盒仓库并接上 `RepoAdapter`，
否则 4 个 kind 里只有 2 个有信号源，驱动冲突根本不会发生**——
而驱动冲突是整个设计的核心（docs/01 §3.1）。

### 7.6 成本

v2 全量 25 次调用、**$0.516**，缓存命中率 19.4%。
比 v1 便宜（每条信号输出 token 少 38%），但缓存命中率下降——
因为按天分批后每批的用户消息更长，稳定前缀占比被稀释。

## 8. ⚠️ 最重要的发现：同一输入，两次运行结果不同

验证并发时用 150 条信号重跑了一次，**输入与全量运行完全相同**，结果却不一样：

```
同样 150 条信号，两次运行
  判断不一致 4 条   →   逐条不一致率 2.7%

其中 08-18 那 100 条：
  第一次运行登记 4 条
  第二次运行登记 7 条      ←  +75%
```

四次翻转全部是「否 → 是」，即第二次更宽松。翻转的都是边界样本：

> 否→是　发育机制/终身技能获取，但落在毫米机器人 RL 技能学习，非动机生成，且闭合条件难写
> 否→是　知识工作 Agent 的版本化工作区，属 harness 工具但非动机/连续性核心

### 为什么 2.7% 的噪声会变成 75% 的波动

因为**登记率本身很低**。100 条里只登记 4~7 条，逐条 2.7% 的翻转率
落到计数上就是 3 条的绝对差——相对波动被放大了一个量级。

**低基率下，小的判断噪声必然被放大成大的计数波动。**

### 对 docs/04 的直接后果

主判据是「自发对账事件数，A 组 ≥5 次/30 天，B 组 ≈0」。
如果底层过程有这种量级的方差，**单次 30 天运行不足以区分 A 与 B**——
A 组跑出 5 次还是 8 次，可能只是同一个过程的两次抽样。

所以：**每组必须重复多次运行，先估计方差，再谈组间差异。**
docs/05 §7 原本说「成本低到可以多跑几个种子」是锦上添花，
现在它是**必要条件**，不是可选项。

这条也解释了为什么 docs/04 §5「无效判据」里要排除"日志读起来很像一个人"——
单次运行的任何观感都可能只是噪声。

## 11. 回放机制第一次兑现（部分）

修正①②的验证完全在录好的 `fixtures/signals.json` 上完成，没有重新采集——
docs/03 §6 的回放机制第一次实际使用。

**「几分钟一轮」的承诺只兑现了一半。** 已给 Intake 加上并发（`WORKERS=6`），
实测 4 批并发耗时 92 秒，串行需约 200 秒，**加速 2.2 倍**。

外推到全量 21 批：6 路并发 = 4 轮，约 **6 分钟**（串行 21 分钟），**约 3.5 倍**。
达不到最初预估的 3.5 分钟——并发下单次调用本身会变慢（50 秒 → 92 秒），
线性外推是错的。

边界要说清楚：**能并发的只是 Intake 这类批内无依赖的步骤。**
日循环本身不能并发——第 19 天的账本取决于第 18 天的结果，那是真实的状态依赖。
